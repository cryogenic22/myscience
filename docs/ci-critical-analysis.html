What the team is building, what I'd build,
and where they differ.

Version 0.1 — review draft Date 2026-05-22 Audience Kapil · Amit · Riya · DS team Scope Experience, agentic engine, backend intelligence Status awaits review + decisions

The team's plan is directionally right and unusually disciplined. The 24-week / 12-epic backlog, the five-step critical path (entity resolution → KBQ views → evidence → framing → learn loop), the agentic UX inversion (Moments-not-feed, agents-propose-humans-dispose, conversational war-game), and the explicit deferral list are all the right moves. I largely agree with the substance.

The differences are at the seams: (a) the home surface — they have Bridge with Moments; I'd argued for a separate Control Tower and now concede their structure is cleaner; (b) dossier sequencing — they treat dossier as week 5–7 of the experience track; I'd argue it's the spine object that subsequent surfaces write into, and the data contract should land earlier; (c) the war-game mode toggle is right but its data contract (trace schema, steer endpoint) needs more shape than PB-1303 gives it; (d) their backend ⓪ (facts ledger) is correctly sequenced — I had silently assumed it was already there; (e) I'd missed multi-tenancy (E11) entirely as a SaaS hard-stop; (f) they have prompt-registry + active feedback (E12), which I didn't spec at all.

Verdict

Adopt the team's plan as the spine. This spec contributes shape in four places they're slightly under-specified — the dossier-as-spine contract, the trace+steer schema, the Twin↔Game-Theory pipeline, and the explicit five-surface experience map. Sequencing matches theirs.

ci-agentic-ux.html — the inversion

A new contract — POST /wargame/{session_id}/steer — for conversational steering in natural language.

3Where I concede to their plan

  1. Drop Control Tower as a separate surface. Bridge with three zones (Pulse · Twin · Moments) already does the integrated-landing job. Keeping a separate Control Tower duplicates and confuses. The agentic-UX doc's stance — "home is Moments" — is the cleaner read.
  2. Adopt the three-agent roster (Sentinel · Strategist · Curator) as the user-facing model, even though six agents may exist in the engine. Users should see three roles with clear verbs; the rest can be internal sub-agents under those banners (e.g. my Synthesizer is inside Sentinel's pipeline; my Twin is inside Strategist's pipeline; my Coach is Curator). Concept-count discipline matters more than completeness.
  3. Adopt conversational war-game steering as the primary interaction. My one-shot "Run War Game" was a prototype shortcut; in production the agentic value is the dialogue. POST /wargame/{id}/steer with mode parameter + trace return is the right contract.
  4. Adopt the ⓪ facts ledger with temporal model (point/interval/anticipatory + valid_from/to + asserted_at + superseded_by). Without this the war-game can't anchor on "Novo's $675 WAC effective Jan 2027" — an anticipatory fact, not a signal.
  5. Adopt multi-tenancy E11 as a hard SaaS-blocker. tenant_id on core entity tables + WHERE-filter middleware + automated isolation tests in CI. Non-negotiable before any external customer.
  6. Adopt prompt registry + active feedback E12. Hardcoded system prompts in services/llm.py are a calibration dead-end. The registry + outcome attribution is what makes the agents actually improve, not just operate.
  7. Adopt authority spectrum (PB-504). L1–L5 with earned promotion via calibration is genuinely good design — it lets agents start cautious (watch / suggest) and earn autonomy. Better than a fixed autonomy parameter.
  8. Adopt their sequencing. Backend critical path before experience polish. My experience-first prototype was useful as a target image; theirs is the correct order to build.

4Where I'd add shape to their plan

Four places the team's docs are slightly under-specified. None requires changing sequencing; all add definition to work already on the backlog.

A. Dossier-as-spine data contract

E3 has 5 stories (PB-301..305) but doesn't articulate the architectural commitment: dossiers are the persistent objects every other surface writes into. A signal arrives → Sentinel updates relevant dossier sections (with provenance). A war-game completes → Strategist writes a "strategic read" section. A decision commits → links to the dossier with the trace. A learn-loop attribution lands → Curator updates the calibration section. Without this commitment, surfaces drift apart; with it, the dossier is the source of truth.

I add the explicit section-level update contract (§9.1) and the dossier-render-as-composition pattern (§7.2). Not new work — new shape on existing work.

B. Trace + steer schema

PB-1303 names the war-game mode toggle and references a steer endpoint, but doesn't define the trace schema. For the trace to be useful (versus a tour-of-internals dump), it needs structured event types: belief-update, option-considered, option-eliminated, simulation-run, recommendation-rendered, each with stable IDs, parent links, inputs, and rendered text. I spec this in §8.4.

C. Twin ↔ Game-Theory pipeline

The two strategy docs mention Twin and Game Theory but as separate things. They aren't — the Twin's belief posteriors are exactly the priors a Bayesian game-theory layer needs. P(Novo cuts WAC by Q1 2027) is a Twin belief; it's also a row in a payoff-matrix priors table. Speccing this as one pipeline (Twin priors → adversary objective functions → payoff matrix → equilibrium output → recommendation → Twin posterior update) closes a real gap. §9.3 + §9.4.

D. Five-surface experience map

The team's surfaces are listed (Bridge · Decision Workspace · War Room · Signals DB · Watchlist · Reviewer · Insights · Catalog · …) but the map — which is hero, which is evidence layer, how a user moves through them — is implicit. I make it explicit in §7. Three hero surfaces (Bridge · Dossier · War Room), one decision-workflow surface (Decision Workspace), one review surface (Reviewer). Everything else demotes to evidence layer. Same conclusion as the agentic-UX doc, just laid out.

5Real tensions worth a conversation

Tension 1 · How aggressive is "agents propose, humans dispose"?

The agentic-UX doc says agents pre-frame, pre-simulate, pre-recommend; the human's job is "judgment, assumption-adjustment, commitment." That's the strongest version of the inversion. PB-504's authority spectrum suggests something more graduated — L1 watch / L2 suggest / L3 recommend / L4 act-with-notice / L5 auto-audit, earned via calibration. The two need to be reconciled: before calibration data exists, what level do agents default to?

My recommendation: start at L2 (suggest), not L3 (recommend), for any new agent type on any new scenario type. A fresh deployment has no calibration record, so "the system already framed and war-gamed your decision" reads as overreach. L2 lets the agent pre-draft the brief and pre-run the war-game, but presents both as "here's a suggestion, please direct the next step" rather than "here's the recommendation, please commit." Promotion to L3 unlocks recommendation language; L3→L4 only with explicit user opt-in per scenario class.

Tension 2 · Where does the human enter the war-game?

Mode ① "autonomous" runs adversary agents and reports back; "humans take decisions where flagged." The escalation rule is currently undefined (inputs needed #2). Three reasonable defaults:

  • Always escalate on commit. Agents play the game; humans always commit. Safe; slow; correct when stakes are real.
  • Escalate on disagreement. If Strategist and the Twin disagree on the recommendation, route to human. Or if the equilibrium has high σ.
  • Escalate on materiality threshold. Above $X EV-at-stake → human; below → auto-committed for review. The L4 model.

I'd default to (a) — always escalate on commit for v1. Strong default; users can opt into (b) or (c) per scenario class once calibration data accumulates. The product-owner-stated requirement ("humans taking decisions where needed") is consistent with this.

Tension 3 · KBQ-as-deliverable vs Moment-as-deliverable

The strategy-roadmap doc keeps KBQs as the "living evidence backbone" but subordinated. The agentic-UX doc puts Moments first. These are compatible — but the team's product copy and surface labels currently mix the two ("KBQ Dossier" is mentioned alongside "Bridge / Moments"). I'd resolve it cleanly:

  • Moments = the workflow trigger (this is what users open in the morning, scan, and act on).
  • KBQ views = a section of every Dossier (this is the parity-comparable competitor view a strategist reads when going deep on one entity).
  • Signals = the substrate (this is what feeds both — visible in Signals DB but not on the home surface).

The two are connected by the dossier: opening a Moment → links to the relevant entity's Dossier → the KBQ section there is already fresh because Sentinel kept it that way. No new work, just the explicit hierarchy.

Tension 4 · Conversational war-game vs structured payoff matrix

The agentic-UX doc has a chat rail; the war-game cockpit (E5) has a payoff matrix view. These are both right for different moments: conversation is for steering ("re-run with this assumption"); the matrix is for reading equilibria. The surface needs to hold both, not pick one. I spec this as a single War Room view with a chat dock at the bottom and the matrix as the canvas (§7.4).

7Experience spec

Five hero surfaces. Everything else is evidence layer (quiet, consistent — not the focus of design polish).

7.1 Bridge — the home

Replaces /ci as the default landing. Three vertical zones:

  • Pulse (left) — last-24h signal stream, filterable by category + entity. Click → Decision Workspace draft.
  • Twin (middle) — 5–10 belief states tracked by the Strategist, each shown as a prior→posterior bar with the driving signal annotated. Click → opens belief detail in the right panel.
  • Moments (right) — 3–8 active Moments ranked by materiality × time-decay, each with EV-at-stake, expiry, and a 1-click open to the Decision Workspace.

One hero strip above: the single most-urgent Moment with a primary action. Mode toggle: live (continuous) / digest_today / digest_week.

7.2 Dossier — the spine

One Dossier per tracked entity (company or product). The architectural commitment: every other surface writes into the Dossier. Signals refresh sections; war-games append "strategic read" sections; decisions link out from sections; learn-loop attributions update the calibration section.

A Dossier renders as a sequence of sections. Section kinds:

  • extracted — facts pulled directly from sources, with evidence pills. (e.g. "Identity", "Pricing & Access", "Trial Activity")
  • kbq — one of the 8 KBQ-views, identical structure across all entities for parity (§9.2).
  • synthesized — Strategist-authored narrative with cited claims. (e.g. "Strategic Read", "SWOT")
  • computed — derived metrics: coverage, freshness, gap-flags.

Per section: coverage (0–1), last_refresh, fact_count, kind, facts[], evidence_ids[]. Click any claim → evidence card.

Contract — Dossier as composition
GET /dossier/{entity_id}
→ {
  entity: { id, kind, name, …profile },
  coverage: 0..1, fact_count, source_count, last_refresh,
  sections: [
    { id, title, kind, coverage, last_refresh,
      facts: [{ text, evidence_ids, signal_ids, materiality }],
      gap_flags: [{ reason, connector_needed }] }
  ],
  linked_decisions: [ decision_id ],   // what was decided about this entity
  linked_moments:   [ moment_id ],     // active Moments touching this entity
  war_room_scenarios: [ ... ]
}

  { source: 'signal' | 'wargame' | 'decision' | 'learn',

7.3 Decision flow — Workspace as document

From the existing 5-panel DecisionWorkspace, evolve to a writing-first composer (TipTap, per PB-401). Sidebar holds: stakeholders, materiality drawer, state. The body is a document with inline AI suggestions (Strategist running every 6s background) and an options grid as an in-document primitive (TipTap node) — not a separate form.

The flow: Moment → "Frame as Decision" → Workspace with pre-drafted question + 2–4 options + cited evidence → strategist edits → "Send to War Room" → war-game runs → recommendation lands back in the Workspace → commit → Reviewer.

7.4 War Room — 3 modes, one canvas

Single canvas, mode toggle at top. Canvas centre: the 2×2 payoff matrix (or n×m when scenarios warrant). Right panel: adversary digital twins with posteriors. Bottom dock: chat rail for conversational steering. Live activity strip showing which agent is doing what.

Modes:

  • Autonomous · adversary agents (competitor / payer / FDA / KOL) play their seats, grounded in the knowledge graph. User watches the trace; receives a recommendation; commits where flagged.
  • Hybrid workshop · user takes one or more adversary seats; AI fills the rest. Designed for facilitated red-team sessions.
  • Game theory · the math layer surfaces. User sets payoffs / priors / objective functions explicitly; reads Nash + Stackelberg + EV distributions. Substrate for modes ① and ②.

Chat dock examples (all valid):

  • "Re-run assuming Novo cuts WAC 50% in Q1 2027."
  • "What if FDA approves CagriSema 60 days late?"
  • "Show me the option Lilly's most likely to pick if we choose option B."
  • "Why did the Strategist eliminate the aggressive play?" (→ trace explanation)

7.5 Reviewer — ledger · replay · coach

Three sub-tabs.

  • Decision Ledger — committed decisions list with linked Moment, evidence, chosen play vs alternatives, calibrated outcome (when review_at lands).
  • Replay — time-scrub for any decision. Shows the world state at T-0 (when committed): the Moment that triggered, the Twin posteriors at that moment, the war-game trace, the evidence weighed. Compares to T-now: what actually happened.
  • Coach — Curator's observations. Pattern detection (anchoring on prior decisions, risk-tolerance drift, calibration wins/losses).

8Agentic engine spec

8.1 Agent roster — three user-facing, sub-agents internal

Three user-facing roles. Internally, each spans multiple specialised sub-agents.

Sentinel
SENSE. User-facing colour: teal. Verbs: watches, clusters, surfaces. Internal sub-agents: Sentinel/Trials, Sentinel/Regulatory, Sentinel/Payer, Sentinel/KOL, Sentinel/Financial, plus a Synthesizer that does cross-stream signal fusion into Moments.
Strategist
FRAME + SIMULATE. User-facing colour: violet. Verbs: frames, simulates, recommends. Curator
LEARN + RECALIBRATE. User-facing colour: amber. Verbs: reviews, learns, recalibrates. Internal sub-agents: Curator/Outcomes (predicted-vs-actual attribution), Curator/Weights (materiality-weight tuning), Curator/Prompts (active feedback to prompt registry).

The user-facing three are the public language; the engine surfaces (Agents tab, AgentActivityFeed) show the internal sub-agents under those banners with full transparency. Three identities for cognitive economy; many agents for operational coverage.

8.4 Trace schema — what makes the agent inspectable

Every agent action emits a trace event. Every trace event has stable id, parent_id (for tree), timestamp, agent, event_kind, inputs (which signals / facts / KBQ items / prior beliefs were consulted), reasoning (model name, prompt_id, system_input_summary), output (what was produced), surface_ref (where the user can see it).

Contract — trace event
{
  trace_id:      "tr_2026-05-22T14:03:01.477Z_a7b3",
  parent_id:     "tr_…",            // for hierarchical traces (a sim has many steps)
  ts:            "2026-05-22T14:03:01.477Z",
  agent:         "strategist" | "sentinel" | "curator" | "adversary:lilly",
  event_kind:    "belief_update" | "option_considered" | "option_eliminated"
               | "simulation_run" | "evidence_consulted" | "recommendation_rendered"
               | "moment_clustered" | "section_updated" | "attribution_landed",
  inputs:        { signal_ids: [...], evidence_ids: [...], kbq_item_ids: [...],
                   prior_beliefs: { tp1: 0.32, tp4: 0.40, … } },
  reasoning:     { model: "claude-opus-4-7", prompt_id: "pmt_strategist_frame_v12",
                   temperature: 0.4, latency_ms: 1840, tokens_in: 4210, tokens_out: 980 },
  output:        { kind: "decision_brief_draft" | "moment" | "play" | "section_update" | …,
                   payload: { … } },
  surface_ref:   "decision_workspace://brief/b_2026_517",
  user_visible:  true | false       // some internal steps are dev-only
}

Default UI: trace shown as a collapsed timeline; expand any node to see inputs / reasoning / output. Per design input #5, this needs a decision on default trace depth (summary vs every step).

9Backend intelligence spec

9.1 Semantic layer — facts ledger (the moat)

Adopting the ⓪ track from the strategy roadmap. Facts are first-class, temporal, append-only:

facts table (Postgres)
CREATE TABLE facts (
  id              UUID PRIMARY KEY,
  tenant_id       UUID NOT NULL REFERENCES tenants(id),
  kind            TEXT NOT NULL CHECK (kind IN ('point','interval','anticipatory')),
  predicate       TEXT NOT NULL,        -- 'wac_usd_monthly', 'fda_approval_date', …
  subject_entity  UUID NOT NULL REFERENCES entities(id),
  object_value    JSONB NOT NULL,       -- typed payload per predicate
  valid_from      TIMESTAMPTZ,
  valid_to        TIMESTAMPTZ,
  asserted_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  source_doc_id   UUID REFERENCES evidence_records(id),
  confidence      REAL NOT NULL DEFAULT 1.0,
  superseded_by   UUID REFERENCES facts(id),
  created_by      TEXT NOT NULL          -- agent or human
);
CREATE INDEX ON facts (tenant_id, subject_entity, predicate, valid_from);

Anticipatory facts are the game-changer for war-gaming: "Novo Wegovy WAC will be $675 effective 2027-01-01" is stored as a fact with valid_from in the future. The war-game queries facts as-of a target date, getting the correctly-timed state. Without this, every "what if X" is hand-rolled.

9.5 Learn loop — closing the flywheel

From the strategy roadmap's ⑤ step. At each Decision's review_at (default: pricing 90d, launch 180d, configurable), the outcome detector runs:

  1. Fetch the actual market state from facts + new signals since commit.
  2. Compare to the Decision's predicted_outcome (the EV-by-option recommendation that landed).
  3. Compute attribution: directionally correct? magnitude correct? Which prior was off?
  4. Write an attribution record (immutable).
  5. Feed back into two places: (a) Twin prior recalibration (the prior that drove the off-call gets re-weighted), (b) prompt-weight backpropagation (the prompts that generated the recommendation get their reliability score updated).

9.6 Prompt registry — versioned + recalibrated

From E12. Move SYSTEM_PROMPTS dict out of services/llm.py:179-250 into the prompt_registry table. Every LLM call references prompt_id; llm_call_log already has the field wired.

A prompt that consistently produces miscalibrated recommendations gets demoted; an alternative gets promoted. Weekly calibration job per prompt + audit log of weight changes.

9.7 Tenancy — non-negotiable

From E11. tenant_id on every core entity table (drugs, companies, trials, mechanisms, signals, evidence_records, facts, decisions, …). NOT NULL after backfill. Query middleware injects tenant_id into every WHERE clause; bypassing the middleware fails the SaaS isolation tests in CI. Cross-tenant data leak is a stop-ship bug.
