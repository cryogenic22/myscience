Competitive Intelligence — Strategy, Roadmap & Build Spec

Version 0.1 (draft for review) Date 2026-05-22 Owner Kapil Audience Kapil · Amit · Riya · DS team (Piyush, Karthik, Pooja) Status Needs review + inputs

We have built the skeleton of the Decision Flywheel and just got the SENSE layer producing real, KBQ-tagged signals in production (469 shipped + 156 in review). Every CI surface renders with zero errors. But the flywheel does not yet turn: signals don't link to competitors, the 8 KBQs are tags rather than living views, evidence chains are cosmetic, and nothing auto-frames a signal into a decision or learns from outcomes.

This document is the honest current-state assessment, the architecture north-star, and a ruthlessly prioritized critical path of the features we absolutely need to deliver the core value — each written as a build-ready mini-spec with reuse pointers, code snippets, acceptance criteria, and the specific inputs we need from you. It is meant to guide development directly, loop by loop.

The one-line strategy

Turn a feed of tagged headlines into per-competitor intelligence a strategist actually uses, then into framed decisions with evidence, then into a loop that learns. Sequenced: ① Entity resolution → ② KBQ living views (dossier) → ③ Evidence chain → ④ Signal-to-decision framing → ⑤ Learn loop.

1The aspiration — the Decision Flywheel

Per specs/CI_Agent_Reimagined_Spec.md, the platform is a closed loop that compresses signal-to-decision latency from 4–12 weeks to under 24 hours for high-materiality signals, and improves its own calibration over time. The eight KBQs are preserved but subordinated: they become the living evidence backbone, not the deliverable.

SENSE→ FRAME→ SIMULATE / WAR-GAME→ DECIDE→ LEARN↺

Three user modes: Always-On Sensing (passive monitoring + proactive alerts), Decision Mode (framing → simulation → recommendation for one question), War-Room Mode (real-time collaborative response). The dossier workflow (specs/comp_intel_2.md) is the day-to-day artifact: a KBQ-answered, parity-comparable competitor profile that an analyst reviews/enriches/approves and that feeds war-gaming. The defensible moat (specs/data_strategy.md) is the semantic layer where every claim carries provenance — click any number, walk to the source.

The value test

We are delivering value when a strategist can (a) open a competitor and see the 8 KBQs answered with live evidence, and (b) receive a framed decision from a material signal. Everything in the critical path serves one of those two outcomes.

4Why the flywheel doesn't turn

  1. No entity spine. Signals aren't linked to canonical entities, so nothing rolls up per-competitor. KBQ views, dossiers, watchlist relevance all depend on this and all fail without it.
  2. KBQs are tags, not views. The deliverable both specs describe — KBQ-answered competitor profiles — does not exist as a queryable artifact.
  3. Evidence is cosmetic. The "click → source PDF" trust spine, which is the entire defensibility argument, isn't wired.
  4. SENSE→FRAME is manual. The defining move of a flywheel (material signal auto-frames a decision) doesn't fire, so it's a feed, not a decision system.
  5. LEARN is open. No outcome attribution → no compounding → it's a dashboard, not an intelligence system that improves.

5Architecture north-star & the pragmatic path

The north-star is the three-layer model from data_strategy.md: Data Plane → Semantic Layer → Intelligence Layer, with an inviolable rule that the intelligence layer never reads raw data — only the semantic layer. The semantic layer's heart is a typed, time-stamped, evidence-linked facts table (point / interval / anticipatory validity) plus a knowledge graph and an append-only event log.

Decision: Postgres-first, retrofit the facts ledger

We do not need Neo4j / Qdrant / Redpanda to deliver the critical path. We build the facts table and a semantic_events log in Postgres, keep pgvector and recursive-CTE graph, and graduate to dedicated infra only if scale demands. This was agreed (Postgres-only, pragmatic). It lets us ship ①–④ on the current stack and layer the full semantic model underneath without rework.

What we reuse rather than rebuild (verified in the codebase):

  • integration/entity_resolver.py — 6-strategy resolution cascade (exact → alias → fuzzy → embedding → LLM → auto-create). Built
  • integration/pipeline_hooks.py — 8 lifecycle hooks incl. POST_STORE, ON_NEW_ENTITY — the insertion point for fact emission. Built
  • services/signal_promoter.py — the producer we just shipped; extend it. Built
  • services/dossier.py + api/routes/dossier.py — composer to point at KBQ views. Partial
  • services/framing_triggers.py — trigger logic for SENSE→FRAME. Partial
  • services/materiality.py, services/game_theory.py, services/learning_service.py — scoring, war-game, learning primitives. Partial

① Entity resolution on signals Next

Missing todayReuses existing resolver

Problem. The producer buckets entityless news as market, so 625 meaningful signals (approvals, deals, readouts) don't attach to Wegovy / Lilly / Novo. Watchlist shows "0 signals match." Nothing can roll up per-competitor — which blocks ②, ④, and the whole dossier workflow.

Reuse
integration/entity_resolver.py (6-strategy cascade) + domain/pharma/mention_normalizer.py
Where
Call resolver inside signal_promoter.build_signal_row when primary_entity_id is null; resolve from the headline/description.
Data
Populate primary_entity_type/id/name + related_entity_ids on each signal; backfill the 625 already promoted.

Target shape

# services/signal_promoter.py — resolve before bucketing
from integration.entity_resolver import EntityResolver

def _resolve_entity(event, resolver: EntityResolver):
    if event.get("primary_entity_id"):
        return (event["primary_entity_type"] or "drug",
                event["primary_entity_id"], event.get("primary_entity_name"))
    # NEW: mine the headline for a company/product mention
    hit = resolver.resolve_mention(event.get("description") or "",
                                   types=("company", "drug"))
    if hit and hit.confidence >= 0.6:
        return (hit.entity_type, hit.entity_id, hit.canonical_name)
    return ("market", "market", None)  # honest fallback retained

Acceptance criteria

  • ≥70% of high-significance signals resolve to a non-market entity.
  • Watchlist on a tracked entity (e.g. Eli Lilly) returns >0 matching signals live.
  • Resolution is logged with strategy + confidence (audit trail); low-confidence routed to HITL queue.
  • Backfill re-resolves the existing 625 signals; deterministic re-run is idempotent.
Input needed

Priority entity set. Confirm the first competitor/product universe to optimize resolution + alias dictionaries for. Recommended start: the GLP-1 field (Novo: Wegovy/Ozempic/Rybelsus; Lilly: Zepbound/Mounjaro/orforglipron; Amgen MariTide; Pfizer danuglipron). Y/N or edit.

Acceptance criteria

  • For a seeded competitor, all 8 KBQ slots return (filled or explicitly "insufficient evidence" — never silently empty).
  • Parity: two competitors return the same 8-slot structure for apples-to-apples comparison.
  • Every KBQ item links to ≥1 evidence/signal id (ties to ③).
  • A completeness score surfaces gaps for analyst enrichment.
Input needed

KBQ definitions sign-off. The 8 KBQs need precise, agreed definitions + the "comprehensiveness gate" per KBQ (what makes KBQ-1 "complete" for a product?). Riya is the right owner — a 1-page definition per KBQ would let us encode the queries exactly. data_strategy.md §5 has draft query shapes to start from.

③ Evidence chain integrity

UI built, data not wired

Problem. Signals cite [event_id], not real evidence_records. The "click any claim → source passage → original document" promise — the platform's entire defensibility — is hollow. We built the cards (Loop #19); we must wire the data.

Reuse
schema/migrations/053_evidence_ledger.sql (evidence_records, append-only) + POST /evidence/by-ids (Loop #19)
Build
On ingestion, write an evidence_records row per source document (source_id, url, retrieved_at, extracted_text, content hash); link signals' evidence_document_ids to those real ids; same for KBQ items.

Acceptance criteria

  • POST /evidence/by-ids resolves a signal's evidence to real source name + tier + date + snippet + URL (not "metadata pending").
  • Every shipped signal and every KBQ item has ≥1 resolvable evidence record.
  • Append-only invariant preserved; superseded evidence retained.
Input needed

Source tiering. Confirm the tier-1 "ground truth" sources (we assume ClinicalTrials.gov, PubMed, FDA, EMA, SEC). This drives confidence tiering and which sources we archive snapshots for.

④ Signal → Decision Brief framing

Triggers + workspace exist

Problem. The defining move of a flywheel — a cluster of material signals auto-produces a framed Decision Brief with options — doesn't fire. Briefs are manual. This is what makes it a decision system, not a feed.

Reuse
services/framing_triggers.py (threshold logic) + services/decision_brief.py + the Decision Workspace UI + services/llm.py for option synthesis
Build
When materiality × confluence crosses a threshold for an entity, synthesize a Decision Brief (question + 2–4 options + stakeholders + horizon), pointing at the KBQ views (②) and evidence (③). Human strategist reviews before simulation (the spec's mandatory gate).

Acceptance criteria

  • A high-materiality signal cluster on a tracked entity generates a draft Decision Brief with ≥2 options and a cited rationale.
  • Brief links back to the triggering signals + KBQ views (traceability).
  • Briefs land in the existing review queue; a strategist can edit/approve/reject before it advances.
Input needed

Trigger thresholds + decision archetypes. What materiality score (and over what window) should auto-frame a brief? And the 3–5 recurring decision archetypes (pricing response, launch timing, portfolio reprioritization…) so option synthesis is grounded, not generic.

⑤ Close the learn loop

Loop openUI + service exist

Problem. Insights/calibration UI and learning_service exist, but no predicted-vs-actual attribution runs. Without it, materiality and recommendations never improve — it's a dashboard, not an intelligence system.

Reuse
services/learning_service.py (EWMA calibration) + services/outcome_detector.py + the Insights UI
Build
At each Decision's review_at, fetch actual market state (from new signals/facts), compare to predicted_outcome, write an attribution record, and feed it back into materiality-weight tuning.

Acceptance criteria

  • Attribution runs on committed decisions at review_at; produces a directionally-correct / calibration record.
  • Insights shows real calibration-over-time (not placeholder).
  • Materiality weights adjust from outcomes (closed loop demonstrable on a seeded decision).
Input needed

Review horizons. Default review_at per decision type (e.g. pricing 90d, launch 180d). And what counts as "outcome correct" for non-numeric decisions.

⓪ Foundation — dedup/clustering + facts ledger Parallel track

Problem. The producer is 1:1 (4× identical CHMP headlines), and there's no facts ledger, so anticipatory facts (e.g. Novo's $675 WAC effective Jan 2027 — the headline war-gaming input) can't be represented. This is the semantic moat from data_strategy.md.

Build (incremental)
(a) dedup/cluster in the producer via event_hash + entity + window; (b) a Postgres facts table (point/interval/anticipatory, valid_from/to, asserted_at, superseded_by, source_doc_id, confidence) + semantic_events append-only log; (c) re-point KBQ views to read facts.

Sequenced after ①–④ prove the value on signals, then retrofitted underneath — so we don't block the visible wins on infrastructure.

Sequencing note

Resist building ⓪ first. It's the most "architecturally satisfying" but delivers no visible value until ①–④ exist to consume it. Build the spine that users feel; deepen the foundation under it.

Glossary

  • Signal — a dedup'd, KBQ-tagged, dual-tier-scored intelligence unit (the signals table).
  • KBQ view — a continuously-maintained answer to one of the 8 Key Business Questions for one entity.
  • Decision Brief — a framed question + options + stakeholders; the SENSE→FRAME handoff.
  • Materiality — 0–100 score for "would this change a KBQ view, recommendation, or simulation?"
  • Anticipatory fact — a future-dated fact (e.g. a price change effective next year) — key war-game input.
