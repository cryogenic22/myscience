CI as a Platform Application

You pushed on two things: (1) “is it really a knowledge base?” and (2) “are we building CI on the sensing + knowledge layer we already have, so one substrate can drive many applications?” This rev answers both with a full substrate inventory (3 codebase sweeps), a concrete reuse-gap table, an honest scorecard, and a remediation plan reframed around composition over the existing platform rather than building a CI silo.

Headline
You’re right on both counts. The platform substrate is real and deep — but my dossier work used almost none of it. It reuses 2 of ~9 available knowledge primitives (facts ledger + engagement FSM) and ignores the entity resolver, hybrid search, graph, metrics, the evidence ledger, and the existing dossier composer. That single choice is what makes it both a content regression and “not really a knowledge base yet.”

The fix is not “build more CI” — it’s re-wire the dossier to compose the substrate that already exists. That also proves the architecture you want: sensing + knowledge as shared services, CI as one thin application on top (war-gaming, catalog, chat are others).

3 · Duplication already creeping in

Smell  Two competitor-dossier builders now exist that don’t know about each other:

  • services/dossier.py · compose_dossier() — the platform entity dossier (signals + evidence + graph).
  • services/war_game_adversary.py · build_competitor_dossier() — a parallel, narrower competitor read for war-gaming.
  • …and now services/dossier_kb.py — a third assembly path that reads facts only.

Three code paths assembling “a picture of an entity,” each from a different subset of the same tables. That’s the silo risk you flagged. The remediation collapses them toward one composed source.

Reframed takeaway: the substrate links score well (sensing/resolution/knowledge ~65–70%). The weak links are the application seams that should compose them — dossier, synthesis, and the dossier→war-game handoff. The platform is more built than my rev-1 implied; it’s the wiring between layers that’s thin.

5 · Remediation — compose the substrate

Re-scoped from rev 1: instead of “fix the facts query,” the goal is “make the dossier a composition of the knowledge layer.” Ordered so each step is observably true and reuses existing code.

LoopFix (reuse-first)Unblocks · acceptance
R1 Resolve the asset via the existing resolver. Replace parse_asset_ref’s slug pass-through with an entity lookup (reuse entity_resolver / drugs-table canonical id). Facts queries hit real entity ids. Acceptance: seeded-DB integration test returns ≥1 non-gap domain.
R2 Compose, don’t single-source. Have assemble_dossier pull from compose_dossier (signals+evidence+related) and facts, normalized into DomainView. No regression vs. legacy dossier; domains populate from all sources. Acceptance: parity test vs. compose_dossier.
R3 Metrics into domains. Feed PharmaMetrics (pipeline strength, competitive_landscape, evidence_density) into clinical/competitive/pipeline domains. Quant-backed domains, no hallucinated math. Acceptance: a known drug shows its real pipeline score.
R4 Competitive breadth via graph. Use graph_analytics.competitive_clusters + the BCB competitive_set to populate the competitive domain with real rivals. Competitive domain reflects the landscape. Acceptance: a competitor appears with a cited edge.
R5 Evidence drill-through. Link facts/claims → evidence_records; make onOpenFact open the source snippet. Reuse evidence_ledger. Every claim is verifiable. Acceptance: clicking a fact shows its source record.
R6 Collapse duplication. Point war_game_adversary.build_competitor_dossier at the same composed source; deprecate the parallel reads. One entity-picture path. Acceptance: war-game competitor view == dossier competitive domain.
R7 Close to the war-game. Auto-populate the BCB from the dossier; feed a dossier snapshot (facts AS-OF scenario date) into the scenario/war-game engines. The keystone feeds the simulation. Acceptance: a war-game run cites dossier-sourced grounding.
R8 Verify the well + integration tests. Run backfill_facts.py, assert facts row count, add real-Postgres integration tests for assembly (the gate rev-1 lacked). “Real” is provable, not asserted from fake-DB unit tests. Acceptance: count > 0; integration suite green.

Recommended next move

Do R1 + R2 together as one loop, gated by an integration test on a seeded Postgres (R8’s gate, pulled forward). That single loop converts the dossier from “narrow facts reader that returns empty” into “a composition of the platform’s knowledge layer” — which is both the honest definition of a knowledge base and the proof that CI is an application on shared substrate, not a silo. R3–R7 then deepen it. I have written no code for this yet — it awaits your go.

6 · The architecture this points to

Your instinct generalizes: the sensing + knowledge layers are domain services, and CI is the first application composed over them. The same substrate drives the Catalog (browse/curate), Chat/GraphRAG (ask), and could drive future apps (a medical-affairs cockpit, a BD&L screener, a payer-strategy desk) — each a thin app that composes resolution + search + graph + metrics + evidence, never re-reading raw tables. The dossier remediation above is the first real test of that contract. If the dossier can be rebuilt as pure composition, the pattern is proven for every app after it.
