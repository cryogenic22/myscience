Issues found, reproduced & fixed

Fixed #1 — Open Targets: silent-zero from GraphQL schema drift

Logged SUCCESS with records_processed=0 on every run; molecular_targets frozen at 128 rows.

  • Reproduced [api]: the drug-detail query returned HTTP 400 — "Cannot query field 'maximumClinicalTrialPhase' / 'linkedTargets' on type 'Drug'". The v4 API retired both fields; targets now live under mechanismsOfAction.rows[].targets[] and the phase field is maximumClinicalStage. The connector caught the 400 and returned an empty target list — fetching 0 records while reporting success.
  • Fix [code: connectors/open_targets.py]: updated the query to the current shape + a tolerant _extract_targets() that reads both new and legacy shapes and dedupes. Live re-run: metformin+semaglutide now yield 11 target records with disease associations (was 0). +4 DB-free regression tests.
Fixed #2 — EMA: silent-zero from page-0 pagination + stale field map + a NameError

Logged SUCCESS proc=0 forever; zero EU trials had ever landed (clinical_trials was 100% clinical_trials_gov).

  • Reproduced [api]: CTIS paginates from page 1 — the connector requested page 0, which returns an empty data array (page 0 → 0 records, page 1 → 88 for semaglutide). The field map used retired EUCTR keys (eudract_number/title/trial_status) vs the live shape (ctNumber/ctTitle/ctStatus/trialPhase/sponsor). And a NameError (RawRecord referenced undefined params; the var is body) dropped any matched record — all swallowed by the broad except.
  • Fix [code: connectors/ema.py]: page 1, real CTIS field mapping, reference body. Live full-pipeline run against prod: 88 processed / 88 inserted / 0 failed → 88 EU-origin trials now in clinical_trials (source_api='ema'). Fetch→resolve→store verified end-to-end.
Fixed #3 — 49 orphaned RUNNING etl_runs made 8 healthy sources look stuck
  • Reproduced [db]: 49 etl_runs rows stuck in RUNNING >6h across mesh (24), clinical_trials (11), pmc (6), pubmed (2), open_targets (2), fda_shortages (2), ema (1), news (1). The pipeline only sets a terminal status inside its own try/except, so a killed process (Railway restart / proxy drop) leaves a permanent RUNNING row — which the scorecard's SYNC dimension correctly flags RED.
  • Fix [code: scheduler/runner.py]: reap_stuck_runs() marks RUNNING rows older than a 12h threshold as FAILED (idempotent + additive), wired at the start of run_now. Ran on prod → reaped 49; scorecard went from 8 RED → 1 RED. +4 tests.
Fixed #4 — SLA blind spots: 3 scheduled sources were invisible to the morning check

FRESHNESS_SLA_DAYS covered only 12 of 15 scheduled sources — NADAC, PubChem, Open Targets had no SLA, so their silent zeros never surfaced.

  • Added all three to the SLA registry (now 15/15) [code: scheduler/config.py].
  • Repointed EMA's SLA from regulatory_milestones (which is actually 100% Orange Book data — the cause of its misleading 3.6% "EMA" link share) to its true store clinical_trials (source_api='ema'), with the shared-table caveat documented.
  • Added a KNOWN_DEFERRED_SOURCES registry so a documented dead source reports DEFERRED, not a false-RED regression.

The scorecard, as a gate

The morning command now scores four dimensions and exits non-zero on any RED, so it gates CI / a cron:

FLOW· STRENGTH· SYNC· E2E→ RED / AMBER / GREEN / DEFERRED
  • FLOW — newest target-table row age vs each source's freshness SLA (the original anti-staleness check, retained & tested).
  • STRENGTH — share of stored rows resolving onto the entity spine via SPINE_FK (FK-NULL share). This is what surfaced EMA's mis-pointed table.
  • SYNC — scheduled? terminal SUCCESS in the last 7d? no stuck-RUNNING orphans?
  • E2E — did the most-recent run actually move rows (records_inserted + records_updated)? The silent-zero detector that caught Open Targets, EMA and NADAC.
