Eval Scorecard — System vs Forge Gold

The measurement layer. The Domain Forge mints gold labels from constrained SME plays (forge_eval_items: prompt → SME answer, by round type). This harness runs the system's own answer for the same prompt and scores it, so we can report accuracy · precision · recall · coverage over time, per round-type and per playbook. Every number traces back to a scored item — nothing is fabricated.

EV-1 + EV-2 shipped
The harness closes the loop: the Forge produces gold, the system answers, the scorer grades, and a run is persisted to eval_runs / eval_results for trend reporting.

No live SME gold exists on prod yet (the Forge is wired but unplayed: 0 forge_eval_items). The metrics on this page are the EV-1 gate run over a small seeded-then-reverted gold set — proof the pipeline scores end to end. Once SMEs play rounds, POST /eval/run scores the real gold set and GET /eval/summary feeds this scorecard live.

0 · How the system is scored, per round type

Each Forge round type elicits a different kind of label; the harness computes the corresponding system answer and compares it. The scorers are pure (no DB) and live in services/evaluation/scorers.py.

5 · The loop, end to end

Forge round→ SME constrained answer→ forge_eval_items (gold)→ EvalHarness.run()→ system answer (planner / routes / materiality / facts)→ score→ eval_runs + eval_results→ GET /eval/summary→ this scorecard
API
  • GET /eval/summary — latest run's metrics + gold-set size + flagged backlog (viewer+). Returns has_run:false until the first run.
  • POST /eval/run — score the gold set now and persist a run (uploader+). Optional playbook_id filter.
  • Programmatic: EvalHarness().run(db) → EvalRunSummary (services/evaluation).

6 · What's next

  1. Get SMEs playing. The harness is only as good as the gold set; prod has 0 plays. Once the Forge UI is in front of SMEs, this scorecard fills with real per-playbook accuracy.
  2. Trend over time. Each eval_runs row is timestamped — add a sparkline of accuracy per playbook across runs (the data is already persisted).
  3. Regression gate in CI. Fail a build if a playbook's accuracy drops below its last run (the run-to-run comparison is a small query away).
  4. Widen critique groundedness. Today a critique cell is "grounded" if any fact of that predicate exists; a stricter check would match the exact claim text.
