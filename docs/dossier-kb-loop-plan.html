How every loop runs

One discipline, repeated. A loop is not "done" until its red-team gate passes and the backlog item is logged.

SPEC→ DESIGN · reuse-first→ BUILD · TDD→ RED-TEAM→ FIX→ GATE PASS?→ LOG PB-Exx + PR→ next
What the red-team checks each loop (so it isn't theatre — these are the exact failure modes that produced my earlier overstatement):
  • Reuse vs. re-implement — grep the new module's imports; duplicating an existing service is a fail.
  • Real data, not fake-DB — every data-path loop adds/extends a seeded-Postgres integration test.
  • Did I overstate? — re-read my own PR text against what the code proves; downgrade any unproven claim.
  • No silent narrowing — composed output must cover ≥ the prior step's.

The 8 loops in detail

PB-E08 · Loop 0 Verify facts ledger + real-Postgres integration tests highinfrarun first
Deliver
A seeded-Postgres test fixture + integration tests for dossier assembly; a verified non-empty facts table.
Approach
Disposable Postgres (pgvector) seeded with a known drug + market_events; run backfill_facts.py. This is the gate harness reused by E01–E07.
Reuses
scripts/backfill_facts.py · event_collector.py · facts_ledger.py
Gate
count(*) FROM facts > 0 on a real DB; integration suite green — not fake-DB unit tests.

Deliver
A resolver step turning engagement.asset ('drug:wegovy') into the canonical entity id before any query.
Approach
Replace parse_asset_ref's slug pass-through with a real lookup; graceful fallback + log when unresolved.
Reuses
integration/entity_resolver.py · search.py (find_similar) · drugs table
Gate
Seeded-DB test: a real engagement returns ≥1 non-gap domain; resolved id matches what event_collector wrote.
PB-E02 · Loop 2 Compose dossier from compose_dossier + facts (no single-source) urgentrefactor
Deliver
Dossier assembled from the existing compose_dossier (signals + evidence + entity_links + related) and the facts ledger, into the 8-domain DomainView. Delivers the PB-1304 composition contract.

Reuses

Gate

Deliver
