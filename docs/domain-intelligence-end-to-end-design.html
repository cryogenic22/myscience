Domain Intelligence — the full spine

How an ask from chat, search, graph or CI is interpreted, decomposed into the right intelligence, retrieved as governed objects, and answered with confidence and gaps — one domain-pack brain driving every surface.

Reconciles chat_domain.md · graph_search_yaml.md · domain_pack_raw.md · YAML_pack1.md · data-intelligence-strategy · with the live code · branch claude/data/domain-intelligence-plan

The SME's diagnosis, in one line. The system answers like a general medical chatbot — it finds vaguely relevant concepts and pads the room — because it generates an answer before building the analytical scaffold. The fix is not "make the chatbot smarter at writing." It is "make it decompose the need first." "The domain pack is the brain. Search is the hands. Graph is the nervous system. The chatbot is just the mouth — a demotion most chatbots richly deserve."

1 · One brain, four surfaces, one spine

Chat, search, graph and the CI app are not four pipelines — they are four entry points to the same domain-pack-driven PLAN stage, which sits on the existing intelligence spine:

Source→Evidence→Extraction→ Resolution+Ontology→Fact→Signal→ Insight→Gap→Scenario→Decision→Learning

Two governed gateways guard the spine, and both are domain-pack-driven:

  • Ingest gateway — semantic resolution (the prior design, Phase 1 shipped): a mention becomes a governed entity at an identity level with confidence, flags and routing. Decides what may become a Fact.
  • Query gateway — the PLAN stage (this design): an ask becomes a decomposed, routed, grounded answer-matrix with coverage and gaps. Decides what intelligence the question actually needs.

4 · Query understanding — the PLAN stage in full

ask (chat/search/graph/CI)→ intent + persona→ ambiguity gate→ select playbook→ decompose → dimensions→ route → predicates/links/sources→ retrieve governed objects→ matrix + coverage + gaps→ answer contract→ synthesise

Ambiguity gate (new)

"success rate / effectiveness / best / winning / likely to succeed" → require disambiguation of lens · denominator · timeframe · geography · indication. Default to a multi-lens answer, never a single confident number. This is the missing piece that turns "GLP-1s are effective" into a five-lens scorecard.

Persona overlays (new)

Same question, different need: a development lead weights phase-transition + endpoint + failure-modes; an access lead weights coverage + PA + step-edits + geography. The overlay re-prioritises and suppresses dimensions — it does not change the facts.

Decompose + route (built)

DecompositionPlanner already turns a playbook into a matrix of DimensionCells, each filled by predicate routes (fact ledger), link routes (graph) and source routes (tables), with a covered/thin/gap state per cell. Reuse verbatim.

Answer contract + quality gates (new)

Every serious answer: interpretation · answer-by-lens · evidence table · confidence · gaps · what-would-change-this · next-best-question. Hard fails: rate without denominator, no timeframe, no gap section, evidence blended with interpretation, generic summary with no retrieved facts.

5 · The data-lane reality check (grounded on prod)

A perfect decomposition over an empty ledger is just structured emptiness. The PLAN stage routes dimensions to fact-ledger predicates — so the question that actually matters for the data lane is: for the SME's five success lenses, can the ledger fill them today?

──────────────────────────────────────────────────────────────────────────────────────────────

regulatory_success        COVERED   1329          —

commercial_success        PARTIAL     20          launch_event, uptake_signal
                                                   Summary: 2 covered | 2 partial | 1 gap
  (pasted from scripts/playbook_predicate_coverage.py against prod, this branch)

The honest reading. Only trial-endpoint and regulatory lenses are truly fillable. development_success looks busy (4201 rows) but every lens-specific predicate is absent — the rows are generic clinical_trial inflation, which the tool deliberately demotes to PARTIAL so a catch-all predicate can't mask a real gap. market-access is an outright gap; commercial is near-empty. So the headline question would decompose into five lenses and render three of them honestly thin — correct behaviour that also pinpoints the data-lane build order. scripts/playbook_predicate_coverage.py makes this a repeatable check (re-run as emitters land).

The data-lane build list this implies

  • Phase-transition / discontinuation emitter (development lens) — from clinical_trials phase + status history. New, high value.
  • Payer / access emitter (access lens) — formulary_status / prior_auth / step_edit facts. Needs a payer-policy source first (the deferred payer ingest). Source-blocked.
  • Sales / launch emitter (commercial lens) — product_sales / launch_event / uptake_signal from filings + launch trackers (the deferred financial/deal emitters, sources mostly empty on prod).
  • These ARE the already-planned loops (latent-data emitters, source-contract registry, the deferred pricing/payer ingest) — now prioritised by what the headline question needs, not by what data happens to be lying around.

6 · Search & graph — governed-object-first, view-driven

Search modes (not one box)

Evidence · Fact · Signal · Gap · Scenario — each returns governed objects (not chunks) with why-retrieved, matched dimension, source class, confidence, freshness, review status. HybridSearch already returns governed SearchResults with provenance; the gap is mode-grouping + dimension binding from the playbook.

Graph views (not a hairball)

One graph, five lenses: evidence-lineage · question-decomposition · entity-network · competitive-landscape · scenario-impact. Every edge carries predicate + evidence count + confidence + freshness + review + contradiction — "a graph edge without evidence is just a rumour with a nice line attached." GraphTraversal already carries edge confidence/provenance; the gap is the views + overlays + bounded expansion.

Decisive rule from the SME: the question-decomposition graph (rendered straight from the playbook matrix) replaces the generic entity neighbourhood as the default answer graph. The plan becomes visible.

9 · Why this is the right architecture

Both gateways share one shape — decompose before you answer; preserve uncertainty; explain; route to governed objects; learn from corrections — and one mechanism: versioned, SME-authorable domain packs driving a generic engine. Chat, search, graph and CI stop being separate toys and become lenses on the same governed intelligence. The chatbot is demoted to the mouth, and the domain pack is finally the brain.

Honest status: this is the design + a grounded data-lane coverage check. The PLAN infra exists but is unwired (Platform lane to switch on); three of five success-lenses are predicate-gaps (Data lane to fill); the UI is Frontend. Nothing here claims to be wired yet — it sequences the real work across the three lanes against what the headline question actually needs.
